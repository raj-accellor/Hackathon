How data moves between the systems: two worked examples

This page traces exactly what one system passes to the next, from the scheduler to the MCP servers, through parsing, Postgres, the metrics engine, the cache, web search and the LLM, and finally to the browser. Example 1 explains every hand-off: what is sent, what comes back, what the receiver does with it, and why. Example 2 lists only the data at each step, so you can work through it yourself and check your answers.

About the data. ABCL and XYZB are made-up companies with made-up figures, chosen so the arithmetic is easy to follow. The message formats (JSON-RPC envelope, tool names, argument names such as endDate / fromDate, and the response fields data, prevClose, next_end_date) come from the tool lists recorded from the live NSE servers (backend/tests/fixtures/live/) and the contract tests. The formulas and thresholds are exactly what the code uses. JSON is trimmed to the fields that matter.

Two separate phases. Phase A (H1–H12) is a background job that runs every evening for every stock and ends with numbers saved in Postgres. No LLM is involved. Phase B (H13–H21) runs only when a user clicks "Research" on one stock. It reads what Phase A saved, adds a live quote and web results, and only then calls the LLM.

1Example 1: ABCL, every hand-off explained

ABC Labs Ltd · NSE symbol ABCL · IT sector · its last trading day was Fri 24 Oct 2026 (close ₹880.00).

Phase A · background job · price history
H1Scheduler→pipeline.prices_jobThe evening job starts
TriggerCron PRICE_REFRESH_CRON = "30 19 * * 1-5" (19:30 IST, after market close). A Redis lock job:prices is taken so two workers can't run the job at the same time. What is passed 
prices_job(container, db_session)
  → ingest_prices(c, s)                           # loops over every active instrument
     → c.market_data.history("ABCL", start=2025-08-01, end=2026-10-27, instrument_type="EQ")
In plain words: the job says "get me about 15 months of daily prices for ABCL". It doesn't say where to get them; the market-data merger decides that.

What the receiver doesStores every tool as ToolInfo(name, description, input_schema). nse_mcp.py then checks its capability list: "history" → bhav → "get_stock_history" is found, so history is supported. "fundamentals" → get_financial_results isn't listed, so it is marked not_supported.
In plain words: the app introduces itself, gets a session id, and asks for the server's menu. It will only ever order items that are on that menu.
H3nse_mcp.py→binding.bind_argsTurning "what we want" into the server's own argument names
Input: our request in our own terms 
{"symbol":"ABCL", "end_date":None, "start_date":2025-08-01, "months":3}
How each one is handled
Our nameMatched toWhy
symbolsymbolexact match
monthsmonths = 3converted to integer (schema says integer)

Output

In plain words: the code never assumes a server's argument names. It reads them from the menu. If a required argument can't be filled, it raises BindError and that capability becomes not_supported instead of sending a bad request.

After the client unwraps it (json.loads on the text)

   … 61 more rows …],

What the client checks
  • result.isError = true → raise McpToolError (never treated as data).
  • A payload with an "error" key, e.g. {"error":"Symbol not found: ABCL"} → ServerRefused, status unavailable.
  • HTTP 5xx or 429 → retried up to 2 times; 5 failures in a row open the circuit breaker for 60 s.
  • HTTP 404 on a session → start a new session and retry once.
In plain words: NSE returns the latest 3 months, newest first, plus a bookmark (next_end_date) saying "ask me for this date next if you want older data".

Safety stops: at most 60 pages · if the bookmark doesn't move back, stop with a warning · if an old page returns an error, keep the pages already fetched and add a warning such as "history starts at …".

In plain words: NSE history prices are not adjusted for splits. This call tells us that on 10 March each share became two, so we know to halve every price before that date.

H13Browser→FastAPIThe research request
POST /api/v1/research/stock      Content-Type: application/json

What the API does before any work starts
  1. Request size checked (too large → HTTP 413).
  2. Body validated by Pydantic (ResearchIn: 1–60 characters).
  3. Rate limit, research bucket, keyed by user + IP (exceeded → HTTP 429 with Retry-After).
  4. resolve_instrument: "NSE:ABCL" → instrument row id 42. An index would be refused.

H17build_evidence→prompt builderChoosing what the LLM is allowed to see
Selection rules
  • From the snapshot's flat: only the ~45 names in EVIDENCE_METRICS, and only if the value isn't null. sector_rs_momentum is null, so it goes into missing_metrics.

  • Each non-null quote field gets Q:<field>; each web result keeps S1, S2…
  • Labels from the score (stance, risk, confidence, entry state) are copied as they are.

Step 2: why did page 3 fail, and why didn't the whole job fail?

NSE has no XYZB data before its listing date, so it returns an error payload. Because pages were already fetched, get_history keeps them and adds a "history starts at …" warning (step 3). The job fails only if the first page fails.

Step 3: the bars are "unadjusted". Is that a problem?

No. get_corporate_actions returned no splits or bonuses, so there's nothing to adjust, and no move above 40% triggered the gap warning. The label stays honest: it says "unadjusted" because no adjustment was applied.

Step 4: what does login_required mean for the data?

Kite couldn't fill gaps or cross-check prices, so coverage is NSE only and there are no conflicts to record. The status is saved in data_source_records and appears on the Data Status page with the login link. Nothing is made up in its place.

Step 7: why is ROCE "not_applicable" and not 0?

sector_kind = "financial". ROCE, EBITDA margin, debt/equity, interest cover, CFO/PAT, EV/EBITDA and FCF yield don't describe banks, so they're marked not_applicable and left out of the pillar's denominator. Fundamentals is therefore 3 out of 3 metrics, not 3 out of 8.

Step 7: why is P/E based on annual EPS here, not TTM?

No quarterly filings were ingested, so ttm() has fewer than 4 quarters and the latest annual EPS (18.0) is used. The earnings basis is recorded as "FY ending 2026-03-31 (latest annual)".

Step 8: why is overall null, and where does 60.0 come from?

The Risk pillar has only 1 of 4 metrics (25%, below the 50% minimum), so it isn't sufficient and the overall score is null. Four pillars qualify (≥3), so a partial score is shown with a disclosure: (62.5 + 58.3 + 64.6 + 54.7) / 4 = 60.0. Momentum has exactly 3 of 6 = 50%, which just meets the minimum.

Step 8: why is confidence Medium, and why is the entry setup "Watch"?

Completeness is 70%, below the 85% needed for High but above 60%, and the data is 3 days old (≤14) → Medium. The trend condition can't be evaluated (SMA200 needs 200 bars), so its result is null. A null doesn't count as a pass, so not all conditions pass → Watch, and the reason is listed under "conditions to wait for".

Step 9: why was the quote a cache hit, and where did it come from?

Someone opened XYZB 25 seconds earlier. quote:XYZB lives for 60 s, so no MCP call was made. The response says "cache":"hit".

Step 10: why are there no S ids, and how does that affect the LLM?

No web search provider is configured, so web.available = false and no sources are collected. The prompt tells the model to leave news and catalysts empty and say web research was unavailable. Any point citing S1 is therefore citing an id that doesn't exist.

Step 11: why was "Sector: momentum positive" kept even though it has no number?

It cites an id that exists (M:sector_rs_momentum) and contains no number that could be wrong. Points are only rejected for missing or unknown citations, numbers not in the evidence, or URLs that weren't retrieved.

Step 12: why is the report "deterministic"?

6 of 10 points were dropped; 6 is more than 10/2 = 5, so the whole model report is discarded. The rule-based report built from the same evidence is shown instead, the reason is shown to the user, and the row is saved with model_id = null.

One-sentence summary: MCP and filings data is parsed into tagged values with their source, merged (NSE first, Kite fills gaps), stored in Postgres, and turned into metrics and scores by plain Python. The LLM only receives a small bundle of labelled evidence; it must cite an id for every point, and any point whose numbers or ids don't match is removed. If too many are removed, the rule-based report is used.
